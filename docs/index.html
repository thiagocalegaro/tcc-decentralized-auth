DOCUMENTAÇÃO VIVA

Autenticação que deixa a chave com você.

O Âncora usa uma carteira Ethereum para provar a posse de uma conta. A aplicação verifica a assinatura, troca um código de uso único e mantém a sessão fora da blockchain.

Decisão centralAssinar, não transacionar.

O login não movimenta fundos, não exige saldo e não grava dados pessoais na rede. A carteira assina uma mensagem curta, vinculada ao domínio, à rede e a um nonce.

SIWE · EIP-4361
01 / escopo

O que o protótipo entrega

A implementação separa interface, API e BFF para que cada camada tenha uma responsabilidade verificável.

01

Identidade por rede

Uma conta vira eip155:chainId:endereço. A mesma carteira em redes diferentes gera identidades distintas.

02

Sessão protegida

O BFF entrega um cookie HttpOnly opaco e impede o acesso a recursos privados sem uma sessão válida.

03

Integração explícita

SDK, API e frontend ficam separados. O fluxo usa PKCE S256, códigos de uso único e asserções ES256.

02 / mapa do sistema

Três camadas, um contrato

O navegador nunca recebe o segredo do cliente nem a asserção assinada pela API.

Prepare o ambiente local

Instale Node.js 22.12 ou superior, npm e Git. Para testar o login, use uma extensão de carteira com conta EOA em Ethereum (1) ou Sepolia (11155111). A assinatura de login dispensa saldo. O modo em memória dispensa banco de dados.

Para uma cópia nova, execute os comandos abaixo. Se você já tem o projeto em C:\Users\get10\projetos IA\TCC II, entre nessa pasta e comece em npm ci.

PowerShell · pasta nova
git clone https://github.com/thiagocalegaro/tcc-decentralized-auth.git
Set-Location -LiteralPath 'tcc-decentralized-auth'
npm ci
npm run setup
npm run dev

setup cria o .env, um segredo de cliente aleatório e a chave ES256 em .local/signing-key.json. Ele preserva arquivos existentes. dev inicia frontend (:5173), API (:3001) e BFF (:3002).

Confira: abra localhost:5173 e consulte /health/ready e /api/health. Os dois serviços devem responder 200.

Configure o cliente e as origens

Edite o .env na raiz. O exemplo abaixo mantém as portas do projeto. Preserve o CLIENT_SECRET gerado pelo setup; a API e o BFF precisam usar o mesmo valor, com pelo menos 32 caracteres.

.env · ajuste estes campos no arquivo existente
WEB_ORIGIN=http://localhost:5173
AUTH_API_URL=http://localhost:3001
AUTH_ISSUER=http://localhost:3001
CLIENT_ID=demo-web
REDIRECT_URI=http://localhost:5173/auth/callback
CHAIN_IDS=1,11155111
STORAGE_DRIVER=memory
SIGNING_KEY_FILE=.local/signing-key.json
CampoComo configurar
WEB_ORIGINOrigem exata do frontend, com protocolo e porta, sem caminho nem barra final. localhost e 127.0.0.1 são origens diferentes.
AUTH_API_URLURL alcançável pelo navegador e pelo BFF. O SDK chama a API nessa URL para criar e verificar desafios.
AUTH_ISSUERIdentificador que a API inclui nas asserções. O BFF exige igualdade com esse valor ao validá-las.
REDIRECT_URIURI registrada que pertence a WEB_ORIGIN. Neste protocolo ela vincula o desafio e a troca de código; o SDK conclui o login por JSON, sem navegar para /auth/callback.
CLIENT_ID / CHAIN_IDSIdentificador do cliente e redes aceitas nos dois backends. O executável atual configura um cliente por ambiente.

Mantenha CLIENT_SECRET, DATABASE_URL e a chave privada ES256 no servidor. O frontend não precisa dessas variáveis; não as exponha com prefixo VITE_.

Ao trocar a porta ou o domínio, ajuste WEB_ORIGIN, REDIRECT_URI e a configuração do servidor Web. Reinicie a API e o BFF depois de editar o ambiente. Para cadastrar vários clientes por código, consulte buildAuthApp({ clients: [...] }) em auth-api/src/app.ts.

Conecte o SDK ao BFF

Dentro deste monorepo, o frontend de demonstração já declara "@tcc/browser-sdk": "*". Ao rodar npm ci na raiz, o npm vincula o workspace. Em outro app Vite/TypeScript, mantenha uma cópia do repositório ao lado do app e instale o pacote local:

Terminal · na raiz do seu outro frontend
npm install "../tcc-decentralized-auth/core/packages/browser-sdk"

Adapte o caminho à sua pasta. O pacote exporta TypeScript e tem private: true; não há um pacote público para instalar com npm install @tcc/browser-sdk. Reutilize o BFF do repositório com npm run dev:bff e a API com npm run dev:api, executados na raiz em terminais separados.

O SDK usa rotas relativas /api/* e cookies com credentials: 'same-origin'. No seu frontend Vite, adicione o proxy abaixo ao server da configuração existente. Ele já está presente no frontend de demonstração.

vite.config.ts · trecho de defineConfig
server: {
  port: 5173,
  strictPort: true,
  proxy: {
    '/api': 'http://127.0.0.1:3002',
  },
},

Preserve o header Origin no proxy. O BFF exige a origem configurada e corpo JSON nas mutações. A API fica em AUTH_API_URL e recebe chamadas do navegador com essa mesma origem.

Confira: GET http://localhost:5173/api/session deve retornar {"authenticated":false} antes do login. Se receber HTML, a rota caiu no frontend em vez de chegar ao BFF.

Implemente o botão de login

Monte este componente na rota pública / do seu app React. Ele descobre carteiras, exige consentimento e inicia a assinatura após o clique. Depois de receber a sessão, navega para /arearestrita.

WalletLogin.tsx · componente completo
import { useEffect, useState } from 'react';
import {
  AuthenticationError, discoverWallets, getSession, signIn,
  type AuthStep, type WalletOption,
} from '@tcc/browser-sdk';

const labels: Record<AuthStep, string> = {
  connecting: 'Conectando à carteira…',
  challenge: 'Preparando a mensagem…',
  signing: 'Confirme a assinatura na carteira…',
  verifying: 'Verificando a assinatura…',
  session: 'Abrindo a sessão…',
};

export default function WalletLogin() {
  const [wallets, setWallets] = useState<WalletOption[]>([]);
  const [selectedId, setSelectedId] = useState('');
  const [consent, setConsent] = useState(false);
  const [checking, setChecking] = useState(true);
  const [busy, setBusy] = useState(false);
  const [step, setStep] = useState<AuthStep | null>(null);
  const [error, setError] = useState('');
  const selected = wallets.find(w => w.id === selectedId) ?? wallets[0];

  // React calls the returned cleanup when this component unmounts.
  useEffect(() => discoverWallets(setWallets), []);
  useEffect(() => {
    let active = true;
    getSession().then(session => {
      if (active && session.authenticated) {
        window.location.replace('/arearestrita');
      }
    }).catch(() => {
      if (active) setError('Não foi possível consultar a sessão.');
    }).finally(() => { if (active) setChecking(false); });
    return () => { active = false; };
  }, []);

  async function login() {
    if (!selected || !consent || busy || checking) return;
    setBusy(true);
    setError('');
    try {
      const session = await signIn({
        provider: selected.provider,
        onStep: setStep,
      });
      if (session.authenticated) window.location.assign('/arearestrita');
      else setError('A sessão não foi criada. Tente de novo.');
    } catch (failure) {
      setError(failure instanceof AuthenticationError
        ? failure.message : 'Não foi possível entrar. Tente de novo.');
    } finally {
      setBusy(false);
      setStep(null);
    }
  }

  return (
    <section aria-labelledby="login-title" aria-busy={busy || checking}>
      <h1 id="login-title">Entre com sua carteira</h1>
      <label htmlFor="wallet-select">Carteira</label>
      <select id="wallet-select" value={selected?.id ?? ''}
        disabled={busy || checking || !wallets.length}
        onChange={event => setSelectedId(event.target.value)}>
        {!wallets.length && <option value="">Nenhuma carteira detectada</option>}
        {wallets.map(w => <option key={w.id} value={w.id}>{w.name}</option>)}
      </select>
      <p>O login compartilha seu endereço público e a rede.</p>
      <label>
        <input type="checkbox" checked={consent} disabled={busy || checking}
          onChange={event => setConsent(event.target.checked)} />
        Concordo em compartilhar esses dados e assinar a mensagem.
      </label>
      <button type="button" disabled={!selected || !consent || busy || checking}
        onClick={() => void login()}>Conectar e assinar</button>
      <p role="status">{checking ? 'Consultando sessão…' : step ? labels[step] : ''}</p>
      {error && <p role="alert">{error}</p>}
    </section>
  );
}
Baixar WalletLogin.tsx ↓Consultar a implementação do SDK ↗

signIn({ provider, onStep }) controla o fluxo: connecting → challenge → signing → verifying → session. O SDK usa descoberta EIP-6963 e fallback para window.ethereum. Você também pode fornecer um provider EIP-1193; o projeto não inclui um conector WalletConnect pronto.

A mudança de conta ou rede durante a tentativa cancela o login. Depois de criar a sessão, trocar a conta da extensão não encerra a sessão do app. Use logout() para isso.

Proteja a área privada e ofereça logout

Monte o componente abaixo em /arearestrita. Consulte a sessão ao carregar a página, trate erros de rede e busque os dados pelo BFF. Você pode usar o roteador do seu app; a demonstração atual controla essa navegação em App.tsx.

RestrictedArea.tsx · componente completo
import { useEffect, useState } from 'react';
import {
  AuthenticationError, getPrivateResource, getSession, logout,
  type AuthenticatedSession, type PrivateResource,
} from '@tcc/browser-sdk';

export default function RestrictedArea() {
  const [session, setSession] = useState<AuthenticatedSession | null>(null);
  const [resource, setResource] = useState<PrivateResource | null>(null);
  const [loading, setLoading] = useState(true);
  const [leaving, setLeaving] = useState(false);
  const [error, setError] = useState('');

  useEffect(() => {
    let active = true;
    async function load() {
      try {
        const current = await getSession();
        if (!active) return;
        if (!current.authenticated) {
          window.location.replace('/');
          return;
        }
        setSession(current);
        const data = await getPrivateResource();
        if (active) setResource(data);
      } catch (failure) {
        if (!active) return;
        if (failure instanceof AuthenticationError && failure.code === 'UNAUTHENTICATED') {
          window.location.replace('/');
          return;
        }
        setError('Não foi possível carregar os dados. Recarregue para tentar de novo.');
      } finally {
        if (active) setLoading(false);
      }
    }
    void load();
    return () => { active = false; };
  }, []);

  async function leave() {
    if (leaving) return;
    setLeaving(true);
    setError('');
    try {
      await logout();
      window.location.replace('/');
    } catch {
      setError('Não foi possível encerrar a sessão. Tente de novo.');
      setLeaving(false);
    }
  }

  if (loading) return <p role="status">Validando acesso…</p>;
  if (!session && !error) return <p role="status">Redirecionando…</p>;
  return (
    <section aria-labelledby="private-title">
      <h1 id="private-title">Área restrita</h1>
      {session && <p>Conta: {session.user.accountId}</p>}
      {resource && <p>{resource.message}</p>}
      {error && <p role="alert">{error}</p>}
      {error && <button type="button" onClick={() => window.location.reload()}>Recarregar</button>}
      {session && <button type="button" disabled={leaving} onClick={() => void leave()}>
        {leaving ? 'Encerrando…' : 'Encerrar sessão'}
      </button>}
    </section>
  );
}

Baixar App.tsx ↓

Proteja os dados no servidor. O redirecionamento React cuida da navegação. Para cada recurso privado, valide a sessão no BFF e verifique a autorização sobre o recurso. O endpoint GET /api/private já retorna 401 sem sessão. Use a função local readSession dentro de buildBffApp como referência ao criar novas rotas; ela não é um helper exportado.

O BFF guarda a sessão e envia um cookie HttpOnly. Você consulta user.accountId, address e chainId pela resposta JSON, sem gravar tokens em localStorage. Se precisar de usuários no seu banco, vincule-os ao accountId validado pelo backend. A prova confirma controle da carteira, sem atribuir papel de administrador ou identidade civil.

No Vite, o cliente faz a verificação da página e o BFF protege a API. Ao servir o build pelo BFF, a rota HTTP /arearestrita também verifica o cookie e redireciona para / sem sessão. REDIRECT_URI não define a página pós-login.

A sessão expira após 30 minutos sem atividade ou oito horas desde a criação. logout() revoga a sessão e limpa os cookies; apenas remover conteúdo da tela não revoga o acesso.

Valide a integração e resolva falhas

Use uma conta EOA de teste e execute este roteiro no navegador do seu app:

  1. Antes do login, consulte /api/session: espere authenticated: false. Consulte /api/private: espere HTTP 401.
  2. Autorize a assinatura, confirme user.accountId e abra /arearestrita. O recurso privado deve responder 200.
  3. Recarregue a página. O BFF deve reconhecer o cookie da sessão.
  4. Encerre a sessão. Recarregue a área privada e confirme outra resposta 401 na API.
  5. Recuse uma assinatura e troque a rede durante outra tentativa. A interface deve mostrar o erro e permitir iniciar um novo fluxo.

Adapte o ambiente de hospedagem

Para preparar um ambiente fora da máquina local, configure HTTPS e os endereços públicos. Este é um roteiro de adaptação do protótipo; a entrega ainda usa sessões do BFF em memória.

  • Sirva o frontend e /api/* na mesma origem pública. Configure no proxy ou no BFF a rota /arearestrita e o atendimento dos arquivos do build.
  • Use AUTH_API_URL acessível tanto pelo navegador quanto pelo BFF. Cadastre WEB_ORIGIN e REDIRECT_URI exatas na API.
  • Com NODE_ENV=production, o executável da API exige PostgreSQL e URLs HTTPS. Configure STORAGE_DRIVER=postgres, a conexão do banco e execute npm run db:migrate.
  • O PostgreSQL persiste desafios e códigos da API. Para várias instâncias do BFF, implemente um adaptador persistente de BffStore para fluxos, sessões e controle de reutilização das asserções.
  • Mantenha chave ES256 e segredo do cliente fora do bundle. Planeje rotação de chaves e limites compartilhados antes de escalar.
Terminal · após configurar ambiente e persistência
npm run db:migrate
npm run build

# Execute em processos ou terminais separados:
npm run start:api
npm run start:bff

O BFF usa frontend/demo-web/dist como pasta de arquivos estáticos. Para servir outro build, configure WEB_DIST_DIR. Ele usa HttpOnly, SameSite=Strict e Secure para HTTPS. O backend precisa reconhecer a sessão em cada recurso protegido.

Filtre por caminho, método ou responsabilidade. A API usa a porta 3001; o frontend acessa o BFF por /api na sua própria origem.

05 / limites

Decisões de segurança

Abra os itens para ver a ameaça, a proteção atual e o próximo passo.

Replay de uma assinatura
A API inclui nonce, domínio, chain ID e expiração na mensagem. Ela consome o desafio na verificação. Próximo passo: armazenar nonces em infraestrutura compartilhada antes de escalar.
Roubo de código de autorização
O código expira em 60 segundos, é de uso único e exige o codeVerifier do fluxo. O BFF troca o código no servidor, sem expor o segredo ao browser.
Carteiras de contrato ERC-1271
A versão atual recupera assinaturas de contas EOA. Para smart wallets, implemente verificação on-chain via RPC, com allowlist de redes, timeout e política de disponibilidade.
Escala horizontal do BFF
Fluxos e sessões ficam em memória nesta entrega. Antes de distribuir instâncias, mova esses estados para Redis ou PostgreSQL e configure rotação de chaves ES256.
06 / linguagem comum

Glossário rápido

Termos usados no código e no texto do TCC.

EOA

Conta controlada por uma chave privada, como uma conta comum da MetaMask.

SIWE

Sign-In with Ethereum: formato padronizado para autenticar uma carteira por mensagem assinada.

PKCE

Par code challenge/code verifier que amarra o início e a conclusão do fluxo.

BFF

Backend for Frontend: camada que guarda segredos e adapta a API para o navegador.

Nonce

Valor aleatório de uso único que impede reutilização de uma mensagem.

JWKS

Documento público com as chaves usadas para conferir as asserções ES256.
